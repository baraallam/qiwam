# Qiwam Database Map

The app now uses custom backend auth against `public.profiles`.

The browser never talks to the database. The frontend calls `/api/*`, and the Express server uses Prisma to read/write Postgres.

## Auth Model

| UI/API field | Database column | Notes |
| --- | --- | --- |
| `id` | `profiles.id` | UUID generated by backend. Also used as `plans.user_id`. |
| `email` | `profiles.email` | Login identifier. Case-insensitive unique index exists. |
| `name` | `profiles.full_name` | One user-facing name field. |
| login name | `profiles.username` | Derived from `name` as lowercase text. Login identifier. Case-insensitive unique index exists. |
| `password` | `profiles.password_hash` | Hashed with bcrypt. Plaintext is never stored or returned. |

Sign-in accepts either:

- email
- name/login name

The server returns a JWT access token. The client stores it in `localStorage` and sends it as `Authorization: Bearer ...`.

## Tables

### `profiles`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `uuid` primary key | User id |
| `full_name` | `text` nullable | Display name |
| `email` | `text` nullable | Email login |
| `created_at` | `timestamptz` | Created timestamp |
| `username` | `text` nullable | Lowercase login/display handle derived from name |
| `password_hash` | `text` nullable | bcrypt password hash |

Used by:

- `server/src/services/authService.js`
- `server/src/services/profileService.js`
- `server/prisma/schema.prisma` model `Profile`

### `plans`

| Column | Type | Meaning |
| --- | --- | --- |
| `user_id` | `uuid` primary key, FK to `profiles.id` | Owner |
| `data` | `jsonb` nullable | Entire planner/spending state |
| `created_at` | `timestamptz` | Created timestamp |

Currently stored inside `plans.data`:

- income fields: `incYou`, `incSpouse`, `incOther`, `customIncome`
- expense estimates: `housing`, `transport`, `food`, `education`, `utilities`, `otherExp`, `customExpense`
- debt/wealth/family fields: `debtPay`, `debtTotal`, `liquid`, `invested`, `age`, `retireAge`, `children`
- assumptions: `ret`, `inf`, `salaryGrowth`, `debtInRetirement`
- goals: `goals`, `customGoals`
- spending tracker state: `categories`, `targets`, `tx`, `fixed`, `salaryDay`, `excludeRecon`, `removedDefaults`

### `categories`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `bigint` primary key | Category id |
| `name` | `text` nullable | Category name |
| `icon` | `text` nullable | Icon |
| `type` | `text` default `expense` | Category type |
| `created_at` | `timestamptz` | Created timestamp |

Current status: exposed in DB, but the frontend stores categories inside `plans.data.categories` with string ids like `food`, `housing_c`, and generated ids.

### `expenses`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `bigint` primary key | Expense id |
| `user_id` | `uuid` nullable | Owner |
| `category_id` | `bigint` nullable FK to `categories.id` | Category |
| `amount` | numeric | Amount |
| `description` | `text` nullable | Note |
| `date` | `date` default current date | Expense date |
| `created_at` | `timestamptz` | Created timestamp |

Current status: not used by the UI yet. Transactions are still in `plans.data.tx`.

### `budgets`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `bigint` primary key | Budget id |
| `user_id` | `uuid` nullable | Owner |
| `category_id` | `bigint` nullable FK to `categories.id` | Category |
| `amount` | numeric nullable | Monthly budget |
| `month` | integer nullable | Month |
| `year` | integer nullable | Year |
| `created_at` | `timestamptz` | Created timestamp |

Current status: not used by the UI yet. Targets are still in `plans.data.targets`.

### `monthly_reports`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `bigint` primary key | Report id |
| `user_id` | `uuid` nullable | Owner |
| `month` | integer nullable | Month |
| `year` | integer nullable | Year |
| `total_income` | numeric nullable | Income total |
| `total_expenses` | numeric nullable | Expense total |
| `created_at` | `timestamptz` | Created timestamp |

Current status: not used by the UI yet. Reports are computed in the frontend from `plans.data`.

## What Is Still Messy

`plans.data` is still a large JSON blob. That is simple and preserves the current app behavior, but it means the existing `expenses`, `categories`, `budgets`, and `monthly_reports` tables are mostly unused.

The next cleanup should normalize spending data:

1. Keep calculator/planner assumptions in `plans.data`.
2. Move spending transactions into `expenses`.
3. Move spending categories into `categories`.
4. Move category targets into `budgets`.
5. Generate monthly reports server-side only if they need to be cached.
